# Hermes Governance Readiness Design

Date: 2026-04-29
Status: Approved design for implementation planning
Scope: Version readiness, signal-family readiness, and daily governance runs after the P20-P30 governance scaffold

## 1. Purpose

Hermes on `codex/quant-governance-p20-p30` has moved beyond the old P20 starting point. The branch now contains a P20-P30 governance scaffold:

- P20-P23 factor logging, cost-aware returns, diagnostics, and shadow calibration
- P24-P26 shadow experiment admission, registration, training datasets, splits, and portfolio evidence
- P28 execution realism
- P29 human production adoption dossier
- P30 evidence-gated advanced model admission

The next optimization path is not to add another model directly. The next path is to turn the scaffold into an auditable readiness workflow.

This design introduces three layers:

```text
VersionReadinessDossier
  -> SignalFamilyReadinessDossier[]
  -> DailyGovernanceRun
```

The work order is:

1. system version readiness review
2. strategy / signal-family readiness review
3. daily governance automation
4. later signal edge improvement using the evidence generated by the first three layers

## 2. Non-Goals

This design does not:

- approve production usage automatically
- mutate production calibration config
- promote shadow model outputs into canonical factor fields
- enable auto-trading
- bypass P22 data-integrity gates
- bypass P24-P30 shadow-only or sandbox-only boundaries
- replace the Phase 19 image-report mainline
- turn a single backtest or diagnostic result into a production decision

All outputs are advisory and human-review oriented.

## 3. Design Principles

### 3.1 Governance before optimization

Hermes should first know whether its current version is ready for human production review. Signal edge improvement comes after evidence quality and review boundaries are stable.

### 3.2 Version before family

Signal-family review depends on a stable system baseline. A family can only be reviewed after the version-level dossier is not blocked.

### 3.3 One-time review before automation

The first implementation should produce a complete one-time review package. Daily automation should reuse that package format instead of inventing a parallel governance path.

### 3.4 Files first, UI later

The first daily governance output should be JSON and Markdown under `output/governance/YYYY-MM-DD/`. Viewer and notification surfaces come later.

### 3.5 Human approval remains explicit

Allowed positive states may say `ready_for_human_review`. No state may mean production approval.

## 4. Layer 1: VersionReadinessDossier

### 4.1 Goal

`VersionReadinessDossier` answers:

> Can this Hermes version enter a human production-readiness review?

It reviews the system version as a whole, not a specific signal family.

### 4.2 Proposed Module

```text
agent/research_v1/version_readiness.py
tests/agent/research_v1/test_version_readiness.py
```

### 4.3 Inputs

Required input groups:

- version metadata:
  - branch
  - commit
  - dirty state
  - optional frozen version label
- test evidence:
  - command
  - status
  - passed count when available
  - failed count when available
  - raw summary string
- P20-P23 evidence:
  - factor snapshot availability
  - net return observation availability
  - P22 validity report availability
  - P23 shadow calibration / observation availability
- P24-P26 evidence:
  - model admission gate status
  - shadow experiment registry status
  - shadow run status
  - dataset / split manifest status
  - portfolio simulation status
- P28 evidence:
  - execution realism report availability
  - liquidity / slippage blocker summary
- P29 controls:
  - rollback plan
  - monitoring SLA
  - version freeze proposal
- P30 evidence:
  - advanced model admission decisions
  - sandbox-only enforcement evidence

### 4.4 Output Contract

The dossier should expose:

- `status`
- `evidence_matrix`
- `test_summary`
- `risk_control_summary`
- `version_freeze_candidate`
- `human_review_questions`
- `next_actions`
- `warnings`

Allowed statuses:

- `blocked_missing_evidence`
- `blocked_test_failures`
- `blocked_risk_controls_incomplete`
- `ready_for_human_review`

### 4.5 Status Rules

The status is derived from evidence and controls:

- missing required phase evidence blocks with `blocked_missing_evidence`
- any required failed test evidence blocks with `blocked_test_failures`
- missing rollback plan or monitoring SLA blocks with `blocked_risk_controls_incomplete`
- complete evidence, passing tests, and complete controls produce `ready_for_human_review`

`version_freeze_proposal` is recommended but not required for `ready_for_human_review`; absence should produce a warning.

### 4.6 Boundary to P29

Existing `phase29_production_adoption_review.py` remains the human adoption dossier primitive. `VersionReadinessDossier` should either:

- compose the P29 dossier directly, or
- produce inputs that can be passed to P29 without translation ambiguity.

It must not weaken P29's rule that production adoption is a human decision.

## 5. Layer 2: SignalFamilyReadinessDossier

### 5.1 Goal

`SignalFamilyReadinessDossier` answers:

> Is this factor family, signal family, shadow model, or advanced model candidate ready for shadow observation or human review?

It runs after version readiness.

### 5.2 Proposed Module

```text
agent/research_v1/signal_family_readiness.py
tests/agent/research_v1/test_signal_family_readiness.py
```

### 5.3 Reviewable Family Types

Allowed family types:

- `factor_family`
- `signal_family`
- `shadow_model_family`
- `advanced_model_candidate`

Examples:

- `quality`
- `valuation`
- `timing`
- `high_conviction_bullish_equity`
- `options_supported_bullish_setup`
- `shadow_meta_model.xgboost_dry_candidate`
- `shadow_advanced_model.real_xgboost_meta_model`

### 5.4 Inputs

Required inputs:

- parent `VersionReadinessDossier` status
- family identity and namespace
- family-specific P20-P23 factor and diagnostic evidence
- P24-P26 evidence when the family is a shadow model
- P28 evidence when execution quality affects the family
- P30 admission evidence when the family is an advanced model candidate

### 5.5 Output Contract

The dossier should expose:

- `family_status`
- `edge_evidence_summary`
- `risk_evidence_summary`
- `degradation_warnings`
- `promotion_forbidden_reasons`
- `allowed_next_step`
- `human_review_questions`

Allowed family statuses:

- `blocked_system_not_ready`
- `blocked_missing_family_evidence`
- `shadow_observation_only`
- `ready_for_human_review`

Allowed next steps:

- `collect_more_evidence`
- `continue_shadow_observation`
- `prepare_human_review`
- `reject_for_now`

### 5.6 Family Status Rules

- If the parent version dossier is blocked, family status is `blocked_system_not_ready`.
- If required family evidence is missing, family status is `blocked_missing_family_evidence`.
- If evidence exists but is not mature enough for human review, family status is `shadow_observation_only`.
- If evidence is complete and no boundary blocker exists, family status is `ready_for_human_review`.

### 5.7 Promotion Boundaries

This dossier must never:

- promote a family to production
- mutate production config
- write shadow outputs into canonical factor fields
- approve advanced models for production

Advanced model candidates must remain sandbox-only even when family status is `ready_for_human_review`.

## 6. Layer 3: DailyGovernanceRun

### 6.1 Goal

`DailyGovernanceRun` answers:

> Has Hermes' evidence chain, shadow experiment state, signal-family readiness, or execution realism degraded today? Are any objects newly ready for human review?

It automates the previously defined one-time review format.

### 6.2 Proposed Module

```text
agent/research_v1/daily_governance.py
tests/agent/research_v1/test_daily_governance.py
```

CLI wiring can be added later through `agent/research_v1/batch_cli.py` or an independent command module.

### 6.3 Run Flow

Daily governance should:

1. collect version metadata
2. collect or receive test evidence
3. collect system-level P20-P30 evidence
4. build `VersionReadinessDossier`
5. build `SignalFamilyReadinessDossier` for configured candidate families
6. write JSON output
7. write Markdown output
8. return a machine-readable summary

### 6.4 Output Paths

Default output directory:

```text
output/governance/YYYY-MM-DD/
```

Expected files:

```text
version_readiness.json
version_readiness.md
signal_families.json
signal_families.md
daily_summary.json
daily_summary.md
```

### 6.5 Daily Summary Fields

The daily summary should include:

- run date
- version status
- blocked items
- new warnings
- stale evidence
- shadow degradation
- human review candidates
- next action queue

### 6.6 Degraded Mode

Daily governance failure should not be treated as research failure. It should mark governance as degraded and explain why.

Allowed daily statuses:

- `completed`
- `completed_with_warnings`
- `governance_degraded`

## 7. Testing Strategy

### 7.1 Version Readiness Tests

Test cases:

- missing phase evidence blocks version review
- test failures block version review
- missing rollback plan blocks risk controls
- missing monitoring SLA blocks risk controls
- complete evidence and controls produce `ready_for_human_review`
- missing version freeze proposal creates a warning, not a block
- serialized status is rebuilt from gate fields where practical

### 7.2 Signal Family Tests

Test cases:

- blocked parent version blocks family review
- missing family evidence blocks family review
- partial but valid evidence produces `shadow_observation_only`
- complete family evidence produces `ready_for_human_review`
- advanced model candidate remains sandbox-only
- promotion-forbidden reasons are present for shadow and advanced models

### 7.3 Daily Governance Tests

Test cases:

- writes all expected JSON and Markdown files
- returns machine-readable summary
- degraded evidence collection produces `governance_degraded`
- daily run does not mutate production config
- daily run can handle zero configured family candidates

## 8. Implementation Order

Recommended implementation order:

1. `version_readiness.py` contracts and pure functions
2. `test_version_readiness.py`
3. `signal_family_readiness.py` contracts and pure functions
4. `test_signal_family_readiness.py`
5. `daily_governance.py` file output orchestration
6. `test_daily_governance.py`
7. optional CLI wiring

The first implementation should prefer standard-library dataclasses and pure functions, matching the P24-P30 style already present in the repository.

## 9. Acceptance Criteria

The design is accepted when:

- version readiness can produce a blocked dossier from incomplete evidence
- version readiness can produce a human-review-ready dossier from complete evidence
- signal-family readiness depends on version readiness
- signal-family readiness preserves shadow-only and sandbox-only boundaries
- daily governance writes JSON and Markdown outputs under `output/governance/YYYY-MM-DD/`
- no implementation mutates production config
- no implementation enables auto-trading
- focused tests pass under Python 3.11

## 10. Future Work

After the readiness workflow exists, optimization should proceed in this order:

1. observe real daily governance runs for evidence gaps
2. add strategy / signal-family review candidates
3. add edge-focused shadow evaluation for selected families
4. compare walk-forward results against prior-only behavior
5. expose governance summaries in the viewer
6. add macOS service scheduling and notifications for blocked, degraded, and newly ready states

Signal edge improvement should be driven by the readiness workflow's evidence, not by ungoverned model additions.
